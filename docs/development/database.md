# Database

Alcove Core stores platform application data in PostgreSQL, accessed through [Drizzle ORM](https://orm.drizzle.team) and [node-postgres](https://node-postgres.com). File contents, such as Drive files, are not stored in PostgreSQL.

## Architecture

[`packages/database`](../../packages/database) (`@alcove/database`) holds Core's database foundation:

| Path                   | Purpose                                                                         |
| ---------------------- | ------------------------------------------------------------------------------- |
| `@alcove/database`     | `createDatabase(url)`: a Drizzle client backed by a `pg` connection pool        |
| `@alcove/database/env` | `databaseEnv(runtimeEnv)`: a T3 Env preset that validates `DATABASE_URL`        |
| `src/schema/`          | Core's Drizzle tables, from the Better Auth milestone (see [Schemas](#schemas)) |
| `migrations/`          | Version-controlled SQL migrations generated by drizzle-kit                      |

- **Core owns this database.** Its tables and migrations live in this package. Modules are deployed independently and must not depend on `@alcove/database` or read Core's tables. They integrate with Core through public contracts and SDKs.
- **Server-only.** Core creates one client per server process in [`apps/core/src/database.server.ts`](../../apps/core/src/database.server.ts) and reuses it for every request. The `.server` suffix and the import protection rule in [`apps/core/vite.config.ts`](../../apps/core/vite.config.ts) fail the build if database code is imported into the client.
- **Lazy connections.** The pool opens connections on the first query, so starting Core doesn't require PostgreSQL to be reachable. A missing or invalid `DATABASE_URL` is reported as a validation error when the server first loads `~/env`, and requests fail until it is fixed.
- **Column names.** The client and drizzle-kit both use `casing: "snake_case"`, so camelCase schema keys map to snake_case columns.

## Local PostgreSQL

[`compose.dev.yaml`](../../compose.dev.yaml) runs PostgreSQL 18 for local development only.

```sh
docker compose -f compose.dev.yaml up -d --wait   # start and wait until healthy
docker compose -f compose.dev.yaml down           # stop (keeps data)
docker compose -f compose.dev.yaml down -v        # stop and delete data
```

The server listens on `127.0.0.1:5432` with user, password, and database `alcove`. Override them with `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, and `POSTGRES_PORT`, set in your shell or a root `.env` file. Data persists in the `alcove-dev_postgres-data` volume.

## Configuration

`DATABASE_URL` is a server-only `postgres://` or `postgresql://` connection URL. Copy `.env.example` to `.env` in each place that reads it:

- `apps/core/.env`: Core, loaded by Nitro during `pnpm dev`.
- `packages/database/.env`: drizzle-kit and the integration tests.

Variables set in the shell take precedence over `.env` files. In production, set `DATABASE_URL` in the process environment.

## Schemas

Core's Drizzle tables will live in `packages/database/src/schema/`, one module per area (for example, `auth.ts`). The directory doesn't exist until the Better Auth milestone adds the first tables.

- `src/schema/index.ts` is the schema entry point. It re-exports every table module.
- `drizzle.config.ts` points drizzle-kit at that file (`schema: "./src/schema/index.ts"`). drizzle-kit collects the tables it exports and compares them with the latest migration snapshot, so a table that isn't re-exported from `index.ts` is left out of migrations.
- `src/database.ts` passes the same module to `drizzle()` as `schema` (`import * as schema from "./schema/index"`). If Core needs the table objects, add a `"./schema": "./src/schema/index.ts"` package export. Core's import protection already blocks it from client code.

Until the first table exists, `pnpm db:generate` exits with "No schema files found": drizzle-kit requires the entry file, and an empty one isn't an option because Oxlint rejects empty modules and `export {}`. `pnpm db:migrate` and `pnpm db:check` don't need it.

## Migrations

Run from the repository root:

```sh
pnpm db:generate   # generate a SQL migration from schema changes
pnpm db:migrate    # apply pending migrations to DATABASE_URL
pnpm db:check      # validate migration consistency (not a schema diff)
```

- `pnpm db:generate` becomes usable once the first schema exists (see [Schemas](#schemas)).
- `pnpm db:check` validates the migration history, such as conflicting migrations from parallel branches. It doesn't preview schema differences, and drizzle-kit has no read-only diff, so review every generated SQL file in `packages/database/migrations/` manually and commit it with the schema change.
- Migrations never run automatically when Core starts. Apply them explicitly with `pnpm db:migrate`.
- Change the schema only through generated migrations. Alcove doesn't use `drizzle-kit push`, which changes the database without migration files.

## Tests

`pnpm test` doesn't need PostgreSQL. Integration tests (`*.integration.test.ts`) run against `DATABASE_URL` separately:

```sh
docker compose -f compose.dev.yaml up -d --wait
pnpm --filter @alcove/database test:integration
```
